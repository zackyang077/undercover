# Swarm and Scoreboard implementation plan

## Goal and starting point

Replace the serial queue agent with a model-free dispatcher. A handler can dispatch the eligible queue at a chosen concurrency, see what happened to each claim, and run the same claim agent against labelled copies on the Scoreboard. The backend owns decisions, payments, run records and scoring.

**Course sidenote.** Build the dispatcher in the style of `labs/week2day4.ipynb` using a LangGraph list node, one `Send` per claim, a worker node and `max_concurrency=N`. Follow `docs/SWARM.md` where it differs from the lab. Product claims retain independent durable threads, traces stay in their claim sessions and carry the run tag, and the backend builds summaries and scores from stored records.

The current Durable build already saves claim checkpoints, gates payments on persisted sign-off and replays decisions and payments safely. Reuse `agent/main.py`, `agent/claim_graph.py`, the attempt and financial operations, and the SQLite/PostgreSQL storage paths. The outgoing queue code lives in `agent/queue.py`, `backend/queue_runs.py`, `backend/instructions_queue.md` and the queue parts of `agent/service.py` and `backend/work.py`. The current browser test corresponding to the brief's run example is `e2e/queue.spec.ts`.

| Component | Responsibility |
| --- | --- |
| Backend | Own the ordered candidate list, run and claim records, telemetry, settlements and evaluation scoring. Serve typed snapshots to the dashboard. |
| Agent service | Admit one dispatch or evaluation, create its run through the backend and execute it in the background. Coordinate individual claim ownership and sign-off resumes. |
| Dispatcher | Fan out eligible claim IDs at the requested concurrency. Call one harness entry point with the claim ID and its run. Isolate worker failures. |
| Harness and claim graph | Admit or recover the claim attempt, work its checkpoint, record usage and active time, and apply existing decision and payment rules. |
| Dashboard | Start dispatches from the queue and evaluations from the Scoreboard. Show stored progress, totals and claim comparisons. |

Tests use stub models, temporary databases and local HTTP stand-ins. Backend APIs use unique `operation_id` values, one-line docstrings and required inputs. During implementation, verify each phase, tick its criteria in this plan, update `docs/STATUS.md` and commit through the pre-commit hook. Run the full checks at handover.

## Phase 1 — Default model, usage and active time

Use `openai/gpt-6-luna` with low reasoning effort by default. A nonempty `MODEL_NAME` is an override and omits reasoning effort. Resolve settings once for a run and record the effective model and effort. Keep the existing claim tools, model call budget and approval flow.

Keep OpenRouter Chat Completions explicit. Record its reply's `usage` in the claim model node before checking the reply for a usable tool call. The pinned `ChatOpenAI` adapter exposes this as `AIMessage.response_metadata["token_usage"]`. Preserve reported token counts and details, and retain sub-cent precision for `usage.cost`. Use one stable write identity per actual provider call. A retried telemetry write reuses that identity and a newly issued provider call gets its own. A missing report stays unknown and a reported zero counts as zero. [OpenRouter usage accounting](https://openrouter.ai/docs/cookbook/administration/usage-accounting)

Pass the executing run ID explicitly into the harness. Usage and work segments belong to that run, or have a null run ID for standalone work, including a separately scheduled sign-off resume. Key them to the claim attempt as well. A later dispatch continuing that thread owns the new work only. Sum active segment durations using a monotonic clock and store UTC boundaries for run timing and concurrency checks. Include time spent in model, backend and checkpoint operations, including their I/O waits. Exclude the human sign-off wait and gaps between invocations, including dispatcher backoff. Keep observed work from failed attempts. Use committed progress for an interrupted segment and surface incomplete measurements when a kill or a missing usage reply leaves a gap. Keep run elapsed time separate from summed claim work.

- [x] A local HTTP stand-in captures the OpenRouter request and verifies Luna with `low` by default and no reasoning field on an override. It returns Chat Completions `usage` and the backend stores the exact token counts and decimal cost, even on an unusable reply. Cases with zero and missing usage remain distinguishable.
- [x] Pytest verifies a lost usage-write response followed by replay leaves one row, a second actual call contributes a second charge, and a failed attempt contributes its reported cost and time. Standalone work is saved with a null run ID.
- [x] With a controlled clock, a claim pauses for sign-off and resumes on the same thread. Stored active time excludes the pause. A thread worked in two runs attributes each segment and model call to its executing run, and a stopped run retains its committed measurements.
- [x] `npm run check:python` passes. An existing Durable database opens with its claim history and settlements intact, and new telemetry storage initializes on SQLite and PostgreSQL.

## Phase 2 — Dispatcher and durable claim recovery

Add `agent/dispatcher.py` with one model-free graph for both run kinds. The list node reads the backend's run membership, ordered for dispatch by `submitted_on` and then `claim_id`. It sends only waiting and recoverable in-progress claims, including payable approvals with signed recovery work if they are available. Skip unsigned holds, settled claims, handler handoffs, evaluation copies in production dispatches, and claims already reserved for a sign-off resume. Persist run membership and claim progress in the backend so the dashboard can report what ran. Compile the dispatcher without a checkpointer. Its worker calls the same harness entry point for new and resumed claim work, and each claim graph keeps its own thread.

Use the worker's `RetryPolicy` for `ModelRateLimitError` and `ModelTimeoutError`, with bounded backoff. Let those provider exceptions escape the existing claim-level retry path so the worker can resume the same attempt at its checkpoint. The worker's `error_handler` reports exhausted transient failures as In progress, ready for a later dispatch. Other failures before a decision close the attempt and return the claim to Waiting. The same dispatch starts its one permitted fresh attempt and gives it a new thread. After two failures the claim goes to a handler. A saved decision takes the existing settlement path on recovery. Keep provider timeouts distinct from the claim deadline and backend HTTP errors.

An isolated stub probe on the pinned LangGraph 1.2.12 found that a multi-`Send` graph can re-raise a handled exception as its executor exits. Keep the current pin and use an independently invoked, stateless one-node graph inside the worker to apply the retry policy and handler. The probe returned all sibling results with that arrangement. The durable claim graph remains behind the harness entry point.

Reuse one ownership check across dispatch, standalone start and sign-off resume. Reserve pending sign-off work before submitting it to the approval executor and recheck eligibility when a worker claims the record. Keep sign-off payment responsive while the graph is busy. Create one `PostgresSaver` per claim invocation on the agent process's shared pool, with setup once per process. Cap the agent and backend at four PostgreSQL connections each, with no overflow, and release a connection at the end of each operation. Keep transactions short through the existing session pooler. [Supabase database connections](https://supabase.com/docs/guides/database/connecting-to-postgres#shared-pooler-session-mode)

- [x] Exercise the pinned LangGraph runtime with multiple `Send` workers, typed `RetryPolicy`, the worker's `error_handler` and no dispatcher checkpointer. A persistent limit or timeout settles that worker's result as In progress while sibling work finishes. Verify this runtime behavior before wiring the full service.
- [x] Stub tests exercise N=1, N=3 and N=25. N=1 proves oldest-first including timestamp ties. A 25-claim fixture records 25 overlapping workers at N=25, and no fixture exceeds its configured N. An empty dispatch finishes cleanly.
- [x] A rate limit and a model timeout both retry from the failed node on the same attempt, without rerunning completed evidence steps. Exhausted waits leave the attempt recoverable by a later dispatch and do not settle it as failed. A different pre-decision error gets a second thread in the same dispatch, and two failures leave the claim with a handler. Fixtures confirm one bad claim never stops its siblings.
- [x] A process break after an evidence, decision or payment step resumes eligible work on its saved thread. Tests race dispatch admission against a committed sign-off and a queued resume, and verify one owner, one decision and one simulated payment. An unsigned hold releases its dispatch slot and remains payable after sign-off.
- [x] Concurrent saver tests verify distinct saver instances share a single bounded pool and queue for checkout rather than open extra connections. A concurrent SQLite integration test exercises actual claim checkpoints. `npm run check:python` passes.

## Phase 3 — Service starts and queue run panel

Add `backend/agent_service.py` for start forwarding and continue sending sign-off notifications after the financial commit. The backend validates and forwards N to the service. The service reserves a shared slot before returning `202 Accepted` with a run ID, then creates the run through the backend and executes it in the background. Release the slot even if creation or work fails. Return `409 Conflict` for a competing start and a clear `503 Service Unavailable` from the backend when the agent service cannot be reached. Poll by the accepted run ID, including the short interval before its record becomes visible. On startup, mark stale running records as Stopped before accepting new runs. Recover independently scheduled signed payments as needed. The next explicit dispatch can take over unfinished dispatch work on its original threads.

Replace the queue controls with an integer N from 1 to 25, default 3. Show the accepted dispatch's claims and statuses, total model cost and elapsed time. On completion, use the stored records to count approvals, declines and referrals, list each payout awaiting sign-off, and list each claim left for a handler or still In progress. An approved hold belongs in both the approval count and the waiting payout list. Save the final snapshot so later work cannot rewrite an earlier run's results. Use the existing claim links and refresh behavior. Keep the instructions screen read-only and show the claim instructions.

Retire the old queue model, queue-specific middleware, instructions, `write_todos`, persisted to-dos and their tests. Remove obsolete cap and continuation controls and the legacy batch CLI. Keep `uv run -m agent CLM-1001` for one claim and `--serve` for development startup. Handle the old to-do table in hosted reseed when present, and preserve existing claim attempts and financial history when opening a Durable database.

- [x] A backend HTTP stand-in captures the requested N. A start returns 202 before the worker finishes, invalid N returns 422, simultaneous requests yield one accepted run and one 409, and an unreachable service yields 503 with no stray run created by the backend. The claim tool list exposes no start operation.
- [x] An injected crash leaves a persisted run visible as Stopped after agent startup. The new service does not start the stale dispatch and the next explicit start restores eligible attempts. An empty or failed run releases admission for the next request.
- [x] A deterministic fixture checks the run panel API against stored decisions, outstanding approvals above the approval limit, handler handoffs, and in-progress claims. Cost and elapsed time agree with run records, and later settlement and dispatch activity preserve the completed summary and totals.
- [x] Vitest and Playwright verify default N=3, validation through N=25, forwarding to the service stand-in, progress on reload, claim links, the final summary, and visible start errors. OpenAPI and the tool registry show the retired queue operations are gone. `uv run -m agent CLM-1001` starts a claim through the stubbed service. An invocation with no claim ID prints usage and exits.
- [x] `npm run check:python` and `npm run check:ts` pass. `npm run dev` still starts all three processes using the existing Windows-compatible Node and uv scripts.

## Phase 4 — Evaluation copies and execution

Seed `data/evals/held_out_claims.json` as a backend-only source and store handler references from `decisions.json` and `held_out_decisions.json` in dedicated tables in the `undercover` schema. Import these with a separate seed step so an existing database can initialize the evaluation records without wiping live claims. The evaluation set uses the 25 queue seed claims. For either set, the backend selects all or the five labelled `tiny` claims and creates the run manifest and its copies together. Record the set, size, N, model and reasoning effort. Each copy's new claim ID is in its record as well as in the manifest. Only the backend's scoring path joins source IDs to handler decisions. Send executable claim IDs and run settings to the service.

Run copies through the same dispatcher, harness, evidence, calculator and claim graph. Give copies their own attempt, decision, activity and simulated-payment records. Resolve their policy, customer and legitimate prior history from the seed evidence so repeat runs see stable inputs. Use the source ID to exclude the original claim from history, and keep live settlements, results from other evaluation copies and handler labels out of the evidence. Filter copies out of the queue, production dispatch admission, direct starts and regular recovery. Block sign-off on copies in the backend before recording or notifying anything. A held approval ends evaluation work with its decision and proposed payout intact. Clear its checkpoint by thread ID, with a repeatable cleanup path for an interruption between recording the result and deletion. When an evaluation is stopped, retain its manifest and partial results for inspection and clean up abandoned checkpoints without resuming the copies.

- [ ] The service work list, copy `get_claim`, bound tool responses and captured model messages contain no handler decisions or payouts from the answer key. - [ ] A held evaluation approval preserves its decision, amount, reason, cost and time, is marked finished, and has no remaining checkpoint. The backend rejects direct sign-off, leaves payment blocked and sends no wake request. A stopped evaluation stays Stopped and a subsequent dispatch never admits its copies.

## Phase 5 — Scoreboard and run traces

Add a Scoreboard view with evaluation starts, newest-first history, and a detail view that can be opened directly and refreshed. Show the run settings and status, with the following backend-computed measures. For scoring, every selected claim has a row. A missing saved decision uses `refer` and zero payout in the formula while the detail indicates that the agent did not decide. Label stopped results as partial and show how many claims were worked. Use integer cents for payout comparisons and error costs.

| Measure | Calculation |
| --- | --- |
| `decision_accuracy` | Share with the same decision as the handler. |
| `accuracy` | Share with the same decision and absolute payout difference of at most $1.00. |
| Cost of mistakes | Sum per claim. Wrong decline $1,500, wrong approval the agent's proposed payout, and needless referral $50. For matching approvals use the absolute payout difference, including differences within $1.00. Matching declines and referrals cost $0. |
| Straight-through rate | Share scored as approve or decline. |
| Model cost per claim | Reported cost for the run, including failed attempts, divided by the number selected. Indicate incomplete usage. |
| Time per claim | Sum of active claim work for the run, including failed attempts, divided by the number selected. |
| Whole-run time | From first claim start to last worker finish or the observed stop boundary. An unstarted run has no work duration. |

Show each agent decision, payout and rationale alongside the handler outcome and payout, with per-claim cost and time. Mark mismatches with text and link to the evaluation copy's claim page. That page has no sign-off form. Follow `docs/BRAND.md` for labels, formatting and readable status colors. Keep the existing per-attempt Langfuse session `<claim_id>/<thread_id>`. Set `langfuse_tags` to include the actual dispatch or evaluation ID on each run-owned trace, including retries, while using the same session under a new run tag when another dispatch resumes that attempt.

- [ ] A seven-row synthetic fixture covers matching approvals off by $1.00 and $1.01, a wrong decline, an unpaid wrong approval at $1,250, two undecided cases against decline and referral, and a correct decline. It yields `decision_accuracy` 4/7, `accuracy` 3/7, straight-through 5/7 and $2,802.01 mistake cost. Hand-calculated token, cost and time fixtures verify per-claim totals, retry and run totals, including overlapping work and a stopped run.
- [ ] Vitest and Playwright start an evaluation from the Scoreboard and verify the service stand-in receives set, size and N. Playwright then plays out an evaluation with the real backend API and sees its metrics, misses, copy links, read-only copy settlement and stopped status. Check newest-first order, refresh, keyboard controls and narrow layout.
- [ ] A test captures the Langfuse config without sending traces. The same thread gets the same session across retry and restart, and two dispatches working it have their respective run tags. A standalone invocation has no run tag. `npm run check:python` and `npm run check:ts` pass.
