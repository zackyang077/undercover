# Week 2 Day 3 实施计划：能等待签批、也能跨进程恢复的理赔

**评审目标**　一笔大额理赔已经获批，理赔员次日打开页面签字。即使原 Agent 进程已退出，新进程也能找到同一笔决定、沿原线程完成模拟付款，并保留签批人和签批时间。验收以业务记录、图的检查点和页面上实际可见的结果为准。

**课程旁注**　已阅读 `labs/week2day3.ipynb`。实施沿用实验的手写状态、节点、条件边、同步检查点和人工中断。实验与 [DURABLE.md](DURABLE.md) 有差异时，以需求文档为准。例如实验直接写付款表，产品图须经后端付款 API；实验用理赔编号做线程号，产品须区分同一案件的不同尝试。以下勾选框留到实施时按实测结果填写。

## 阶段 1　先接入赔付试算和逐案追踪

先在现有单案入口验证两个可独立观察的结果。模型根据证据判断承保范围、选择给付项目及费用明细。后端按 `labs/week2day1_payout.py` 的顺序计算金额，通过绑定当前案件的工具把逐项计算返回给模型。参照 `labs/week2day1.ipynb` 在调用处接入 Langfuse，后续换图时沿用同一套 session 命名。

- [x] 新增只试算的 `POST /api/claims/{claim_id}/payout-calculation`。由后端关联保单、计划、附加险和公司设置，要求传入 benefit、明细及第三方已赔金额（无则传 0）。返回 `calculation`、`payout`、`needs_sign_off`。所有新增 API 均有唯一 `operation_id`、单行 docstring，输入均必填。
- [x] 离线算例覆盖按件数和电子附加险限额、现金合计上限、酒店房晚和无票餐费，再按第三方退款、适用免赔额、给付上限（含行程成本）、最低零元计算到分。例如 Premium 行李险一件电子产品损失 1,500 美元，附加险限额 1,200，已获赔 100，免赔 50，应返回 **1,050 美元、须签批**。重复试算不会写入决定或付款。
- [x] 修改测试库中源自 `data/company.json` 的 `payout_approval_limit`，试算与付款门禁同步变化。默认设置下 1,000.00 美元免签，1,000.01 美元须签。脚本模型通过 HTTP 调用工具，保存的决定保留计算说明、条款及手册引用。
- [x] 单案启动、队列委派和后续恢复共用确定的 Langfuse session ID（如 `CLM-1003/<thread_id>`）。假回调验证同案同线程聚合、不同线程隔离；无追踪配置时，单元测试仍可断网完成。实际跨签批 trace 在阶段 6 经 API 核实。

## 阶段 2　将业务数据和检查点放到可重启的存储

保留现有记录键、金额精度、活动顺序及老数据读取行为。开发启动器显式传入环境。后端仅在进程环境含 `DATABASE_URL` 时使用 Supabase session pooler，否则继续使用 `UNDERCOVER_DB` 选择 SQLite。移除 `agent/main.py` 导入时的 `load_dotenv()`，使测试导入产品模块不会带入个人配置。

- [x] 将 SQLAlchemy 加入正常 `uv sync` 的依赖，锁定实际使用的驱动/检查点依赖。把业务表、guidance 初始化、队列和事务中的原生查询迁到 Core。一次业务事务复用同一连接；对并发准入、当前队列快照和同案写入使用数据库约束及原子更新。SQLite 测试证明并发开案不抢同一案、不超 cap、不丢待办。
- [x] Postgres 每条业务及检查点连接设置 `search_path=undercover`。在此 schema 初始化业务表和同步 `PostgresSaver` 表，复用有上限的连接池，计入检查点连接后**每进程合计最多 4 条**，关闭溢出连接配额，退出时释放。集成检查记录实际表所属 schema 和连接数。
- [x] 给无云配置的本地运行使用可重新打开的文件型 SQLite 检查点；测试使用独立临时文件。重开旧版 SQLite 样本，已存决定、签批、付款、尝试、活动和当前队列仍可读；正常重启同一数据库不会重复播种。测试进程显式隔离云端变量。
- [x] 扩展 `backend/reseed.py`，保留显式 SQLite 路径和备份行为，增加选定 Supabase 项目的开发播种入口（拟用 `npm run seed`）。远端仅重建本产品在 `undercover` 的业务记录与检查点，保留 `lab`、`public`。在指定的验收库重新播种后，25 案均为 Waiting，旧运行、支付和可恢复线程均为零，随后再次正常启动仍是 25 案。

## 阶段 3　先让后端能安全处理重放，再接图

决策或付款可能已提交，但调用进程在收到响应或写下一个检查点前就退出。以每案唯一的业务记录作为判断依据，在事务中写入或取回既有结果。调用方用返回的完整理赔详情决定下一步。

- [x] 同案两次 `POST .../decision` 提交相同的 `DecisionInput`，均成功返回当前理赔，决定只一条且原创建时间不变。比较规范化的业务字段（包括以分计的金额、理由、计算、引用），排除服务端生成的时间和署名。改变决定或其业务内容返回 409。并发相同请求也只落一条。
- [x] `POST .../payment` 对相同全额重放返回当前理赔，只产生一次模拟付款。错额、分拆、无批准或拒赔/转人工均不可付。超限未签返回 403；边界金额、并发请求以及“已提交但丢响应”都有回归用例。
- [x] `POST .../sign-off` 由合格理赔员提交，只保存签批事实、人员和时间。直接读详情与队列验证：超限未签为 `waiting_sign_off`，已签未付为 `in_progress`，付款后为 `decided`。付款记录关联原签批人和签批时间，另记实际付款时间。普通拒赔或转人工仍是已有终局决定。

## 阶段 4　用同步 LangGraph 推进单案

图保存 claim ID、尝试 thread ID、消息、模型调用预算和已得出的决定。新案从调查开始；每个同步步骤通过 `durability="sync"` 写入检查点。业务金额、签批及付款事实始终从后端读取。拟沿用现有决策字段，把模型提出的决定保存在图中，再由独立节点提交，避免提交后重放时重新生成理由。

| 上一步的结果 | 下一步 |
| --- | --- |
| 模型需要证据或试算 | 调用当前案件的 HTTP 工具，记录结果/拒绝原因，回到模型 |
| 有完整决定 | 提交决定；业务输入被拒时把原因返回模型修正 |
| 后端确认拒赔或转人工 | 记录结果，结束单案 |
| 后端确认批准且可付款 | 付款节点调用现有全额付款 API，核实付款后结束 |
| 后端返回 `waiting_sign_off` | 在独立节点调用 `interrupt()` 并释放工作线程。收到已保存的签批后恢复，再进入付款节点 |

- [x] 脚本模型走通试算→保存决定→直接付款、拒赔、转人工、超限暂停四条路径。调查工具保留证据/条款读取，移除模型可调用的 `pay_claim`，同步更新 `backend/instructions.md`。移除 `Runs.conclude` 的补付路径，普通批准和签批后批准均由图调用付款。
- [x] 节点保留原有活动记录、章节全文与版本、工具拒绝信息、暂时性错误的有界重试及执行期限。模型调用计数跨检查点保存并包含重试，最多 30 次；等待签批的时间不计为运行超时。离线验证持续请求工具的模型达上限后不会发出第 31 次调用，也不会虚构决定。
- [x] 用文件检查点和新实例重建图。进程被中止时，原线程从最后成功步骤继续（已有可执行检查点用 `invoke(None, ...)`）；人工中断只有在后端已存签批后才用同线程 `Command(resume=...)`。在决定和付款提交后、各自检查点写入前注入故障，重启后保持原尝试且各只有一条业务记录。
- [x] 修正等待签批即完成、重启即失败的旧判定。签批中断释放当前队列 helper，后续案件可继续。真正的执行错误若尚无决定，则保留失败历史，回到 Waiting，用新线程和空消息再试一次；两次失败后交给人工。已有决定的恢复只补剩余步骤。旧库已获批、缺图检查点的未付案件也能依据已有决定接入等待或付款步骤。

## 阶段 5　把签批通知、队列恢复和页面连起来

新增独立 Agent 服务和 `agent/__main__.py`。页面仍通过业务后端启动队列、单案和签批。后端保存运行信息，Agent 服务运行同步图，队列继续用 `create_agent` 选择和委派案件。服务与 `uv run -m agent` 共用调度入口。签批通知只是及时唤醒线程的信号，数据库里的签批才是恢复凭据。

- [ ] `npm run dev` 在 macOS 和 Windows 兼容的脚本中启动前端、后端和 Agent。服务默认地址 `http://127.0.0.1:8002`，后端可用 `UNDERCOVER_AGENT` 覆盖；CLI 可启动运行。开发启动时传入 `.env`，测试不加载该文件。验证模块入口、服务健康检查及 dashboard 的单案/队列启动。
- [ ] 签批事务成功提交后，后端在后台通知服务，响应不等付款。让测试服务故意延迟或离线，签批请求仍成功，理赔保持已签未付。服务重启或下次运行先找中断案和已签未付案，再领新案；尚未签批的线程继续等待。通知早于等待检查点落盘、重复通知、以及恢复扫描与通知同时到达时，对同一线程串行推进，最终一次付款。
- [ ] 从保存的批次接续原范围、目标、已占名额、待办和单案线程；下一次运行先完成停止批次的剩余工作。保留“当前案结束后停止”的按钮语义。用 cap 为 5 的脚本批次在第二案中途终止，再启动。原案尝试数不变，最终处理 5 个不同案件，重试不多占名额，已完案件不会重新决策，批次摘要和待办与业务记录一致。
- [ ] `DecisionPanel` 的按钮改为 **Sign off**。页面只发签批请求，`Workspace` 在已签未付期间持续刷新详情和列表，即使批次已经结束或用户重新加载页面。Vitest 验证 Waiting for sign-off → In progress → Paid，显示签批人及时间，不再显示可再次签批或手动付款的操作。
- [ ] Playwright 沿用 5174 测试前端、8010 测试后端，另在 **8003** 启动 Agent 替身，并显式将测试后端指向它。通过页面签批一次，替身收到对应案件通知，能从后端读到已提交签批；浏览器没有发送付款请求，测试不访问 8002。真实图恢复并支付一次的证明由 Python 集成测试给出。
